Hi, we’re team Mandate. Every company that lets someone other than the owner spend money has the same problem, and AI agents are about to make it much worse. Mandate is a small, strict layer between the people and agents who ask to pay, and the PayPal account that actually pays. The one sentence to remember: anyone can ask to pay; only the warrant — rules the owner wrote — and the owner’s own tap can pay. Let me show you who this is for.

The insight06 / 15
PayPal already wrote the rule

“The user who creates a payout cannot approve the same payout.”

PayPal Developer Docs · Payouts · payout approval flow

PayPal today

For people, in a dashboard, with fixed approvers.

→
Mandate

For agents, at the API, with rules the owner wrote.

Maker ≠ checkerMandate
The insight came from PayPal’s own documentation. In the Payouts web dashboard there’s an approval flow, and the docs say: the user who creates a payout cannot approve the same payout. That’s maker-checker, the oldest control in finance. But it only exists for humans clicking in a dashboard, with fixed approvers and no rules. Mandate brings that exact principle to the API, where the one creating the payment might be an AI agent.

🔒 No path

from the model to PayPal. No secret, no approve tool, no payout tool.

ArchitectureMandate
Here’s the whole system in one line. Arun types a sentence. Our clerk — a free open-weights model — is an MCP client of our own MCP server, which offers exactly three tools: propose, list, explain. The proposal hits the warrant gate, a pure function that never calls PayPal, and gets one of three answers: deny, auto, or needs approval. Only an approval signed by Meera’s passkey can reach PayPal Payouts, and only for the locked cents. A verified webhook updates the ledger, and the packet records it all. The key line is the bottom one: there is no path from the model to PayPal.

Invariants, enforced in code and testsMandate
We publish three rules, and every feature follows from them. One: the model proposes; it never authorizes and never holds the PayPal secret. Two: AI can only add friction. If our risk signals see something odd, they can turn an automatic payment into one that needs Meera — but nothing the AI says can ever turn a denial into a payment. Three: every dollar has a packet that anyone can verify. These aren’t slogans; each one is a test in the repo.

AI architecture14 / 15
Three roles, three privilege levels

Small model. Zero authority. On purpose.

Reader

No tools. Output is strict JSON, checked by Zod.

Payee picked from warrant ids. Integer cents. Must echo the server’s clause.

Backtested on past requests. Meera publishes with her passkey.

Swap the model — the money stays safe. Safety lives in the server.

0

Dual-LLM pattern · MCP · Zod-validated tool callsMandate
The AI is deliberately narrow. Three roles with different privileges. The reader reads untrusted text — vendor emails, PDFs — and has no tools at all; it just outputs strict JSON. The clerk is an MCP client of our own MCP server; it picks payees from a list of warrant ids, uses integer cents, and its reply must repeat the server’s clause. The warrant compiler turns Meera’s plain words into a typed rule change, backtested before she signs it. And it all runs on a free twenty-billion-parameter open model. That’s the point: the model holds no authority, so you can swap it and the money stays safe.
